# MSSQL Backup

Небольшой веб-интерфейс для резервных копий Microsoft SQL Server: создание и восстановление копий,
вход через LDAP с ролями, история действий пользователей, выбор хранилища (папка, SMB, S3).
Работает без Docker: Nginx + Python-служба под systemd.

```
браузер ──► nginx (:8080) ──► API (gunicorn/Flask, 127.0.0.1:8000) ──► SQL Server
                 │                    │                                     │
              web/index.html     /var/lib/mssql-backup               BACKUP / RESTORE
                                 (настройки, история)             прямо в папку, SMB или S3
```

Сервис **не читает и не пишет `.bak` сам**: команды `BACKUP`/`RESTORE` выполняет SQL Server и сразу пишет
в выбранное хранилище. Поэтому папку бэкапов не нужно монтировать на веб-сервер, а список копий берётся из
журнала SQL Server (`msdb`).

## Установка (Debian / Ubuntu)

```bash
tar xzf mssql-backup.tar.gz && cd mssql-backup
sudo ./deploy/install.sh            # или: sudo PORT=80 ./deploy/install.sh
```

Скрипт ставит `nginx` и `python3`, создаёт пользователя `mssql-backup`, виртуальное окружение в
`/opt/mssql-backup`, службу `mssql-backup`, конфиг `/etc/nginx/conf.d/mssql-backup.conf` и службу применения сертификата `mssql-backup-tls`. Пароль локального
администратора генерируется и печатается в конце. Затем впишите подключение к SQL Server:

```bash
sudo nano /etc/mssql-backup/mssql-backup.env      # MSSQL_HOST, MSSQL_USER, MSSQL_PASSWORD
sudo systemctl restart mssql-backup
```

Обновление: распаковать новую версию и снова запустить `install.sh` (настройки и история сохраняются).
Удаление: `sudo ./deploy/uninstall.sh` (`--purge` удалит ещё и настройки с историей).
Логи: `journalctl -u mssql-backup -f`.

Права учётной записи SQL Server: проще всего `sysadmin`. Минимально: `dbcreator`, `db_backupoperator` на нужных
базах, чтение `msdb` (список копий) и `ALTER ANY CREDENTIAL` (только для S3).

## Интерфейс

Страница адаптивна: на экранах от 1280 px (Full HD 1920×1080 и больше) рабочая область расширяется до ~1700 px, а на вкладке
«Копии» карточки «Создать копию» и «Восстановить копию» стоят рядом, «Сделанные копии» — на всю ширину ниже; диалоги
пользователя и группы показывают три списка баз в ряд. На узких экранах всё складывается в одну колонку.

## Роли и группы доступа

| Роль | Что можно |
|---|---|
| **Полный доступ** | всё, включая раздел «Настройки» |
| **Копии и восстановление** | видеть списки и историю, создавать копии, восстанавливать |
| **Просмотр** | видеть список копий и историю, без действий |

Право подтверждать запросы на создание баз — не роль, а признак внутренней группы (см. ниже); оно есть и у всех с полным доступом.

* **Локальный администратор** (`ADMIN_USER` / `ADMIN_PASSWORD` из `/etc/mssql-backup/mssql-backup.env`) всегда имеет
  полный доступ и входит даже при неверных настройках LDAP, так что заблокировать себя нельзя.
* Пользователям LDAP роль выдаётся по группам: в «Настройки → Авторизация LDAP» для каждой роли задаётся DN группы.
  Роль определяется по атрибуту `memberOf` (прямое членство, вложенные группы не раскрываются); при нескольких группах
  берётся высшая роль; пользователь вне этих групп войти не может.
* Роль фиксируется при входе и действует до выхода или до истечения сессии (12 часов).

## Куда можно восстанавливать: пользователи, группы, запросы

Роли выше определяют, *что* можно делать. Куда именно разрешено восстанавливать, задаётся отдельно, в
«Настройки → Пользователи» и «Настройки → Группы».

* **Пользователи.** Список пополняется автоматически при первом входе из LDAP (локальный администратор в списке не
  нужен). Для каждого можно отметить базы, в которые ему разрешено восстанавливать, и назначить внутренние группы.
* **Три независимых доступа к базам** (для пользователя и для группы; права складываются: личные + все группы):
  * **Создание копий** — для каких баз можно делать копии: только они видны в карточке «Создать копию», для остальных
    `/backup` отвечает `403`;
  * **Источники восстановления** — чьи копии можно брать в «Восстановить копию»: только эти базы попадают в список «База»
    и в список копий; копию чужой базы нельзя развернуть даже как новую базу (`403`);
  * **Куда восстанавливать** — какие существующие базы можно перезаписывать.
  Списки не зависят друг от друга: например, можно разрешить делать копии базы A, брать копии баз A и B как источник и
  перезаписывать только B. По умолчанию все три пусты, полный доступ ограничений не имеет. `/databases` без параметров
  отдаёт объединение трёх списков (для роли «Просмотр»), `/databases?for=backup` — только базы для копий. При обновлении
  со старой версии оба новых списка («копии» и «источники») заполняются из прежнего общего списка (или из баз,
  разрешённых для восстановления). «Очередь» и «История» по-прежнему показывают задачи других пользователей целиком.
* **Внутренние группы** живут только в этом приложении и не связаны с группами LDAP. Группа может
  (а) разрешать восстановление в отмеченные базы и (б) подтверждать запросы на создание новых баз. Права
  пользователя = личные базы + базы всех его групп. Участниками можно назначить только тех, кто уже входил.
* **Форма «Восстановить копию»** (на вкладке «Копии», сразу под «Создать копию», перед «Сделанные копии»; роли «Просмотр» вместо
  формы показывается пояснение; над формой выводится строка «Ваши права»): выбирается база, из
  последней копии которой нужно восстанавливать, и «Восстановить в»: список содержит только разрешённые существующие базы,
  последний пункт — «Восстановить как новую базу» с полем для имени. Кнопка — «Добавить в очередь».
* **По умолчанию** ничего не отмечено, поэтому список существующих баз **пуст**, а новую базу создать можно, но
  только через запрос: он появляется на вкладке «Запросы» (со счётчиком), и его подтверждает участник группы с
  признаком «подтверждает запросы» или пользователь с полным доступом. Свой запрос подтвердить нельзя — нужен другой человек.
  После подтверждения восстановление стартует сразу, в истории оно записано от имени автора запроса со ссылкой на
  подтвердившего. Автор может отменить запрос, пока его не обработали.
* **Полный доступ** ограничений не имеет: любые существующие несистемные базы, новые базы без запроса.
* **Защищённые базы** («Настройки → Защита баз»). Для отмеченных баз перезапись возможна только после подтверждения
  администратором. Оператор с правом на такую базу выбирает её в списке (в нём она помечена 🔒), вводит имя для
  подтверждения, и вместо восстановления уходит запрос; параметры (в том числе «отключить подключения») берутся из
  запроса. Подтвердить или отклонить такой запрос может **только пользователь с полным доступом** — участники
  внутренних групп подтверждения не могут, счётчик «Запросов» им такие запросы не показывает. Пользователи с полным
  доступом восстанавливают защищённые базы сразу. Защита не даёт права на базу: тот, у кого её нет в списке
  разрешённых (лично или через группу), её в списке по-прежнему не видит.
* **Перезапись существующей базы** всегда требует ввести её имя. Если выбранная база — не та, из которой сделана копия,
  файлы копии по порядку переносятся на файлы выбранной базы, поэтому число файлов данных и журнала должно совпадать
  (иначе — «восстановите как новую базу»). Системные базы в списки не попадают и восстановлению не подлежат.
* Изменения групп и подтверждающих действуют сразу (интерфейс обновляет права раз в 30 секунд, повторный вход не нужен);
  роль LDAP по-прежнему читается при входе.

## HTTPS-сертификат из доменного центра сертификации

«Настройки → Сертификат» (только полный доступ) позволяет получить сертификат для веб-интерфейса в центре сертификации
домена (например, Microsoft AD CS) и установить его без правки конфигов:

1. **Запрос (CSR).** Укажите имя сервера (CN, например `backup.corp.local`), дополнительные имена/IP (SAN; CN добавляется
   в SAN автоматически), при желании организацию, подразделение, страну, область, город и размер ключа RSA (2048/3072/4096).
   Сервис создаёт закрытый ключ и CSR командой `openssl` (расширения: `subjectAltName`, `keyUsage`, `serverAuth`).
   CSR можно скачать (`.csr`) или скопировать. Закрытый ключ остаётся на сервере и в браузер не передаётся; новый запрос
   заменяет прежний неустановленный.
2. **Получение сертификата.** Отправьте CSR в центр сертификации: веб-регистрация AD CS (`/certsrv` → «Расширенный запрос»,
   шаблон «Веб-сервер») либо `certreq -submit -attrib "CertificateTemplate:WebServer" mssql-backup.csr`. Сертификат
   сохраните в Base64 (.cer / PEM).
3. **Установка.** Загрузите файл или вставьте текст PEM. Принимаются PEM (в том числе цепочка), DER (`.cer`/`.crt`) и
   PKCS#7 (`.p7b`). Сервис проверяет, что сертификат выдан по созданному на сервере ключу, срок действия, выбирает лист и
   выстраивает цепочку (корневой сертификат в неё не включается), предупреждает, если имя из запроса отсутствует в
   сертификате. Затем он передаёт файлы отдельной системной службе `mssql-backup-tls` (запускается от root по
   `mssql-backup-tls.path`, скрипт `/opt/mssql-backup/tls-apply.py`): она повторно проверяет ключ и сертификат, кладёт их в
   `/etc/ssl/mssql-backup` (ключ `0600`, только root), формирует конфигурацию nginx (HTTPS на выбранном порту, по умолчанию
   443; по желанию HTTP перенаправляется на HTTPS), выполняет `nginx -t` и перезагружает nginx. При любой ошибке прежние
   сертификат и конфигурация возвращаются, причина показывается на странице. После успеха копия ключа удаляется из каталога
   службы.

Безопасность: веб-служба работает без прав root и не может менять nginx сама — только оставляет запрос в
`/var/lib/mssql-backup/tls`, содержимое которого скрипт root считает недоверенным (файлы читаются без перехода по ссылкам,
ключ и сертификат перепроверяются и перезаписываются через openssl, в конфигурацию попадают лишь фиксированные пути и
числовые порты). Установщик `install.sh` при обновлении сохраняет настроенный HTTPS. Продление — повторите шаги 1–3
(страница показывает срок действия и подсвечивает, когда осталось меньше 30 дней). Клиентам нужно доверять корневому
сертификату вашего центра (в домене AD это обычно уже так).

## Хранилище копий

«Настройки → Хранилище копий по умолчанию». Кнопка «Проверить запись» делает пробную копию базы `model` в выбранное
место (файл `mssql_backup_web_write_test.bak`, перезаписывается; в списке копий не показывается).

| Тип | Что указать | Условия |
|---|---|---|
| **Папка на сервере SQL** | путь так, как его видит SQL Server (`/var/opt/mssql/backup`, `D:\Backups`) | у службы SQL Server есть право записи |
| **SMB** | UNC-путь `\\fileserver\backups\sql` | SQL Server **на Windows**; пишет от имени учётной записи своей службы, логин/пароль SMB здесь не задаются. На Linux-версии SQL Server UNC не работает — смонтируйте шару на самом сервере SQL и используйте тип «Папка» |
| **S3** | endpoint, порт, бакет, папка, Access/Secret Key | SQL Server **2022+**; HTTPS с сертификатом, которому доверяет ОС сервера SQL (на Linux — положите CA в `/var/opt/mssql/security/ca-certificates`); бакет уже существует; Object Lock выключен; файл копии ≤ 100 ГБ; разница часов с S3 ≤ 15 минут |

Для S3 сервис сам создаёт на SQL Server credential `s3://endpoint[:порт]/бакет` с вашими ключами (он пересоздаётся
при каждой операции) — права `ALTER ANY CREDENTIAL`. Access Key не должен содержать `:`. Ключи хранятся в
`/var/lib/mssql-backup/settings.json` (права 0600) и обратно в интерфейс не отдаются.

**FTP не поддерживается.** SQL Server не умеет писать на FTP, а читать его папку веб-сервис не может (она не
примонтирована). Если FTP нужен, смонтируйте FTP-каталог на сервере SQL (например, curlftpfs) и укажите его как «Папку».

## Копии и восстановление

* Копия создаётся командой `BACKUP DATABASE … WITH COPY_ONLY, CHECKSUM, COMPRESSION`, поэтому цепочку разностных копий
  она не нарушает. Файл называется `<база>_<ГГГГММДД_ЧЧММСС>.bak`.
* Описание под заголовком «Создать копию» (куда складываются копии, `COPY_ONLY`) видит только администратор; `/info` с местом хранения и адресом SQL Server тоже только для него.
* **Очередь.** Копии и восстановления не выполняются сразу, а встают в очередь («Копии» → «Сделать копию» и «Добавить в
  очередь»). Один рабочий процесс берёт задачи по порядку, по одной, поэтому две операции на SQL Server одновременно не идут.
  Вверху меню «Очереди»: там задачи всех пользователей (позиция, кто добавил, что и куда, статус) и последние завершённые;
  счётчик показывает число ожидающих и выполняющихся. Ожидающую задачу может снять её автор или администратор, выполняющуюся
  снять нельзя. Очередь хранится в базе службы и переживает перезапуск (выполнявшаяся в этот момент задача получает статус
  «прервано», остальные продолжатся). Подтверждённые запросы на создание/перезапись тоже встают в эту очередь. Настройки
  хранилища читаются в момент выполнения, а не постановки в очередь.
* **«Недавно завершённые»** (меню «Очереди»): администратор видит задачи всех пользователей, остальные — только свои.
  Пользователям результат показывается в сокращённом виде: пути к файлам и хранилищу заменяются на `…/имя_файла`
  (то же в самой очереди; искать по скрытой части пути тоже нельзя). Над таблицей есть фильтры по столбцам, как в истории:
  дата завершения (с / по), пользователь (только администратору), операция, объект, статус, текст в результате; список
  подгружается кнопкой «Показать ещё». Вкладка «История» не менялась и показывает полные результаты.
* **«Сделанные копии» видны только администратору** (полный доступ): список полных копий из `msdb` (включая сделанные не
  через этот сервис) с путями к файлам; API `/backups` для остальных ролей закрыт. Список **постраничный**: размер страницы
  10 / 50 / 100 / 500 записей (по умолчанию 50, выбор запоминается в браузере), внизу — номера страниц со стрелками
  «Назад / Вперёд» и строка «Записи 51–100 из 132». Разбивка выполняется на стороне SQL Server (`OFFSET … FETCH`), поэтому
  большой журнал не загружается целиком.
* **Выбор копии при восстановлении.** В форме «Восстановить копию» после выбора базы появляется список «Резервная копия»:
  первый пункт — **«Использовать последнюю резервную копию»** (по умолчанию), дальше все копии этой базы от новых к старым
  (до 200) с датой и размером. Пути к файлам пользователи не видят: копия передаётся своим номером (`backup_set_id` из
  `msdb`), сервер сам проверяет, что копия относится к выбранной базе. Администратор может, кроме того, нажать «Восстановить»
  в строке «Сделанных копий» — нужная копия подставится в список. Имена файлов всё же могут быть видны в «Истории» и «Очереди»
  (текст результата операции).
* **Уведомления** («Настройки» → «Уведомления», только администратор): когда задача очереди завершилась, сервис может
  отправить сообщение по **e-mail** (SMTP: STARTTLS, SSL/TLS или без шифрования, логин/пароль необязательны) и/или на
  **Telegram** (бот: токен от @BotFather + id чата или @канал; сообщение уходит через `api.telegram.org`; если прямого выхода нет — можно указать **прокси только для Telegram**: HTTP/HTTPS (с логином и паролем) или SOCKS5 (имя хоста резолвит прокси); системные переменные `HTTP_PROXY` игнорируются; пароль прокси после сохранения не показывается) и/или в
  **Bitrix24 (облако)** (входящий вебхук с правом «Чат и уведомления (im)», вызывается `im.message.add`; получатель —
  id пользователя или `chatN` группового чата) и/или на произвольный
  **webhook** (POST JSON `{"text", "event", "database", "job", "user", "status"}` — Slack, Mattermost, Rocket.Chat, свои
  обработчики). Галочками выбирается, о чём сообщать: копия создана / ошибка копии / восстановление выполнено / ошибка
  восстановления. Есть кнопки тестовой отправки (работают и с ещё не сохранёнными полями). Пароль SMTP, токен Telegram, URL вебхуков Bitrix24 и webhook (в них токены) не показываются после сохранения. В поле «Результат» уведомления у созданной копии — **имя файла и размер** (например, `sales_20261022_030000.bak, 1.23 ГБ`; размер берётся из журнала SQL Server, при сбое запроса уходит только имя), у восстановления — то же, что в очереди, но путь к файлу заменён его именем (`sales_….bak -> sales2 (перезапись)`); путь в уведомлениях не отправляется. Ошибки копирования передаются как есть. Отправка идёт в отдельном потоке, поэтому медленная почта очередь не
  тормозит; если сообщение не доставлено, это видно в «Истории» (действие «Уведомление», статус «ошибка»). Запросы на
  подтверждение (создание/перезапись базы) отдельных уведомлений не создают — сообщение придёт, когда подтверждённая задача
  выполнится.
* **Восстановление** (одинаково для обеих форм):
  * с исходным именем — база **перезаписывается** (`WITH REPLACE`); нужно набрать имя базы для подтверждения, есть
    опция «отключить активные подключения» (`SINGLE_USER WITH ROLLBACK IMMEDIATE`, после — `MULTI_USER`);
  * с новым именем — создаётся новая база, файлы кладутся в папки данных/журналов SQL Server по умолчанию; существующую
    базу с таким именем так не затереть;
  * системные базы (`master`, `model`, `msdb`, `tempdb`) восстановить нельзя.
* Скачивания и удаления `.bak` в интерфейсе нет: файлами управляет SQL Server и хранилище (очистка старых копий — задача
  администратора хранилища).

## История действий

Вкладка «История» (видна всем ролям): вход и выход, добавление пользователей, неудачные попытки входа (с причиной
и IP), запросы на создание баз (создание, подтверждение, отказ, отмена), изменения прав и групп, создание и
восстановление копий (статус, длительность видна по времени, текст ошибки SQL Server), изменения и проверки настроек
(какие поля менялись; значения секретов не пишутся). Есть фильтры по действию, статусу и пользователю.
Хранится в `/var/lib/mssql-backup/history.db` (SQLite), по умолчанию 365 дней (`HISTORY_KEEP_DAYS`).
Если служба перезапущена во время операции, запись получает статус «прервано».

**Доступ.** Вкладка и API истории всего сервера (`/history`) доступны только роли «Полный доступ» (локальному
администратору и группе LDAP с полным доступом). Остальные видят свои задачи в «Очередях»; по номеру своей задачи
(`/history/<id>`) им отдаётся только её статус и результат с сокращёнными путями — чужие записи и не-задачи (входы,
настройки и т. п.) недоступны (`404`).

## Безопасность

* Пароли LDAP-пользователей нигде не сохраняются; пустой пароль отклоняется до обращения к LDAP (иначе «анонимный bind»
  у некоторых серверов проходит успешно); логин экранируется в LDAP-фильтре.
* Защита от перебора: 10 неудачных входов с одного IP — блокировка на 5 минут. Сессия — подписанная HttpOnly cookie,
  `SameSite=Lax`; изменяющие запросы требуют заголовок `X-Requested-With` (защита от CSRF). Все эндпоинты API закрыты
  по умолчанию, права проверяются на сервере.
* Вход идёт по паролю — **включите HTTPS** для всего, что дальше доверенной сети: «Настройки → Сертификат» (см. ниже). Cookie сессии получает флаг `Secure` автоматически, когда страница открыта по HTTPS (`COOKIE_SECURE=true` в настройках службы принудительно включает его всегда).
* Для LDAPS/StartTLS с сертификатом внутреннего CA укажите `LDAP_CA_FILE` в файле настроек.
* Служба работает от отдельного пользователя с ограничениями systemd; Nginx слушает все интерфейсы на выбранном порту —
  ограничьте доступ файрволом при необходимости.

## Ограничения

* Восстановить можно только копии, записанные в журнал `msdb` этого SQL Server.
* Нет расписания и автоматической очистки старых копий. Очередь простая (по порядку добавления): приоритетов и
  перестановки задач нет.
* Нет уведомлений о новых запросах (e-mail и т. п.): подтверждающий видит счётчик на вкладке «Запросы».
* Группы LDAP читаются из `memberOf` (AD и OpenLDAP с overlay `memberof`); вложенные группы не раскрываются.
* Один процесс API (так задумано, см. unit-файл): масштабирование на несколько воркеров не предусмотрено.

## API

Все пути под `/api/`, запросы не-GET требуют заголовок `X-Requested-With: fetch`.

| Метод | Путь | Роль | Описание |
|---|---|---|---|
| POST | `/auth/login`, `/auth/logout` · GET `/auth/me` | — | вход, выход, текущий пользователь |
| GET | `/info`, `/databases` | любая | хранилище, базы |
| GET | `/backups?limit=10\|50\|100\|500&offset=` | полный | страница списка копий из msdb с путями: `{backups,total,limit,offset}` |
| GET | `/queue` | любая | активная очередь всех пользователей и последние завершённые (администратору все, остальным свои; пути сокращены) |
| GET | `/queue/recent` | любая | завершённые задачи с фильтрами `action,status,user,target,text,from,to,limit,offset` |
| POST | `/queue/<id>/cancel` | автор / полный | снять ожидающую задачу с очереди |
| GET | `/restore/sources` | копии | базы, у которых есть копии, и дата последней (без путей) |
| GET | `/restore/copies?database=` | копии | все копии базы: id, дата, размер (без путей) |
| POST | `/backup` `{database}` | копии | поставить копию в очередь → `{id,position}` |
| GET | `/restore/targets` | копии | базы, в которые можно восстанавливать этому пользователю |
| POST | `/restore` `{database,target,new,confirm,kick_users}` | копии | поставить восстановление в очередь → `{id,position}`: перезапись (`new=false`, `confirm`=имя базы) или новая база (`new=true`; без полного доступа создаёт запрос → `{request}`). Источник — копия `copy` (id из `/restore/copies`; она должна относиться к `database`) или, если `copy` не указан, последняя копия `database`; поле `path` (конкретная копия) допустимо только с полным доступом |
| GET | `/requests` · POST `/requests/<id>/approve`, `/reject`, `/cancel` | запросы | запросы на создание баз; решает подтверждающий, отменяет автор |
| GET/PUT/DELETE | `/access/users[/<логин>]` | полный | пользователи: свои базы и группы |
| GET/POST/PUT/DELETE | `/access/groups[/<id>]` | полный | внутренние группы |
| GET/PUT | `/access/protected` | полный | список защищённых баз (`{databases:[…]}`) |
| GET | `/history?limit&offset&action&status&user` | полный | история всего сервера |
| GET | `/history/<id>` | любая | запись истории: полный доступ — любая, остальные — только своя задача (пути сокращены) |
| GET/PUT | `/settings/ldap`, `/settings/storage`, `/settings/notify` | полный | настройки (секреты не возвращаются) |
| GET | `/settings/tls` | полный | установленный сертификат, неустановленный запрос, статус применения |
| POST/GET/DELETE | `/settings/tls/csr` | полный | создать запрос `{cn,sans,org,unit,country,state,city,key_bits}` / скачать CSR / отменить |
| POST | `/settings/tls/install` `{certificate\|certificate_b64,https_port,redirect_http}` | полный | проверить и передать сертификат на установку |
| POST | `/settings/ldap/test`, `/settings/storage/test`, `/settings/notify/test` `{channel: email\|telegram\|bitrix24\|webhook}` | полный | проверка |
